# 0.2.0の質問・選定・記録仕様

作成日: 2026-11-01

状態: **カタログ0.2.0と`balanced-choice-v1`の実装仕様。** 質問の内容は[カタログ](../catalog.json)、計算と保存結果の検証は[選定器](../selection.py)、保存と表示は[設定プログラム](../configure.py)に対応する。

Lは説明の構成を選ぶ内部制御値である。質問は考えるときの足場を尋ね、IQ・知能・能力・性格を測定しない。以下の対応、重み、閾値、順序は独自の暫定規則であり、本人への適合や理解改善を実証した心理尺度ではない。文献の位置づけと未検証の効果は[根拠と背景](evidence-and-design-rationale.md)にまとめている。

[旧設計案](level-design-v02.md)の32選択肢と最大点での補正は採用していない。旧案の文字や確認ケースを、この0.2.0の表へ読み替えない。

## 1. 何を変え、何を保つか

| L | 説明の主な構成 |
| --- | --- |
| 80 | 具体的な一件の対象・操作をたどり、条件・理由・判断・行動をつなぐ |
| 90 | 利用者が示した目的と、役割のある作業のまとまりをつなぐ |
| 100 | 選択肢を共通の判断基準で比較する |
| 110 | 条件によって判断や行動がどう分かれるかを示す |
| 120 | 要素間の関係と、一つの変更が他へ及ぼす影響を示す |
| 130 | 説明・判断の捉え方を比較し、採用理由と見直す観察条件を示す |

全Lで必要な事実、理由、前提・条件、例外、不確実性、次の行動を保つ。調査・推論・実装・レビュー・検証の品質や速度を意図的に下げない。正確さや反例の検討を特定のLだけに与えず、不要な試行・比較・別の枠組みを増やさない。今回の明示的な依頼とプロジェクトの要件を、保存済み方針より優先する。

同じ相談を六つの構成で書き分けた全文の参照例は、[旧設計案の第2節](level-design-v02.md#2-同じ相談への6種類の回答例)に残している。これらは執筆した説明例であり、モデルを動かして得た評価結果ではない。

## 2. なぜ8問×6択へ変更したか

8つの場面と問いは0.1.0から保持し、各問の通常選択肢を4つから6つへ改訂した。各問で六つのアンカーを一度ずつ提示し、一つの通常選択肢を一つのアンカーへ直接対応させる。

| 観点 | 0.2.0での扱い |
| --- | --- |
| 問数 | 固定8問を維持する |
| 選択肢 | 通常32個から48個へ50%増える。理由や長文の自己説明は求めない |
| 各アンカーの機会 | 各問に1選択肢、全体で8選択肢・8設問。単独回答の上限はどれも24点 |
| 表示位置 | 設問ごとに変更する。各アンカーがA〜Fそれぞれに現れる回数は1回か2回 |
| 直接支持 | 選択肢が明示する一構成へ加点する。共通の支持を分母の差で区別しない |
| 残る課題 | 文章の自然さ、読み分けやすさ、位置の影響、本人への適合は別に確認する |

8問×4択の32個を一対一で6アンカーへ割り当てると、提示回数を整数で完全にそろえられない。8問×3択なら各4回にできるが、各場面で三つの構成を候補から外すことになる。今回は、全場面で六つの構成から選べることを優先した。

この変更は数学的な提示機会をそろえる。意味の重複や選ばれやすさまで等しくしたという意味ではない。特に100の「案を共通基準で比べる」と130の「捉え方自体を比べる」が読み分けられるか、q6の目的へ戻る選択が自然に読めるかは未確認である。数字の順序や10刻みも、心理的な距離から求めていない。

## 4. 得点と支持設問数

通常回答が一つなら、そのアンカーへ3点を加える。二つなら主回答へ2点、副回答へ1点を加える。通常回答のある一問の合計は、どちらも3点になる。`context`・`none`・`skip`は0点で、通常回答数にも含めない。

```text
score(a) = 各選択の「対応アンカーがaなら、その重み」を全問で合計
support(a) = aに加点した異なる設問IDの集合
answered_count = A〜Fの通常回答がある設問の数
```

全アンカーを同じ素点で比較し、アンカーごとの最大値で割らない。各問に六つすべてを置くため、回答されたどの設問でも全アンカーを選べる。重み3・2・1は「一問の総量を固定し、主回答を副回答より重くする」ための独自規則であり、重要度を実測した係数ではない。

たとえばq1の`["A", "C"]`は80へ2点、90へ1点である。`["C", "A"]`は90へ2点、80へ1点になる。二つ選んでも一問を二問の支持として数えない。選ばれた副回答は、そのアンカーに対する一つの設問の支持にはなる。

## 5. 判定の順序と理由

先に素点と支持設問を計算し、正の最大点を持つアンカーの集合を`top_candidates`とする。点が一つもなければ、この集合は空配列になる。そのうえで次の順に判定する。

| 順序 | 条件 | L | `selection.reason` |
| --- | --- | --- | --- |
| 1 | 通常回答のある設問が3問未満 | 仮設定100 | `insufficient_answers` |
| 2 | 最大候補がない、または最大候補の**どれか一つでも**支持が2問未満 | 仮設定100 | `insufficient_support` |
| 3 | 最大候補が一つ | そのアンカー | `matched` |
| 4 | 最大候補がちょうど二つで、差が10 | 二候補の中点 | `adjacent_blend` |
| 5 | 最大候補が非隣接の二つ、または三つ以上 | 仮設定100 | `mixed` |

支持不足は、同点の判定より先に扱う。隣接する二候補が同点でも、片方が一問からしか支持されていなければ`insufficient_support`となる。最大候補全体の支持設問を合算せず、**各最大候補**を確認する。最大候補が支持不足のとき、下位候補を繰り上げない。

通常回答3問以上・最大候補ごとに支持2問以上という閾値も、少ない回答への依存を避けるために置いた暫定規則である。十分性や選定精度を実証していない。

`matched`の100は比較構成が規則上選ばれた値である。`mixed`・`insufficient_answers`・`insufficient_support`の100は利用開始のための仮設定であり、比較構成を本人が支持したと記録しない。離れた候補の平均を取り、支持されていない構成を選んだ理由にすることも避ける。

## 6. 入力と保存する計算過程

### 外部から受け取る入力

入力のトップレベルは`catalog_version`と`answers`の二つだけである。`level`、`evidence`、`selection`、独自の個人指示や推測した属性を受け取らない。全8問を含め、通常回答は異なる1〜2個の文字を順位順の配列で指定する。版の不一致、未知の選択、重複、特別な回答との混在、設問の不足は受け付けない。

以下は**0.2.0用の架空入力**で、利用者本人の回答ではない。各問で100に対応する選択肢を一つ選んでいる。

```json
{
  "catalog_version": "0.2.0",
  "answers": {
    "q1": ["E"],
    "q2": ["D"],
    "q3": ["C"],
    "q4": ["B"],
    "q5": ["A"],
    "q6": ["F"],
    "q7": ["A"],
    "q8": ["F"]
  }
}
```

手計算では100に8問×3点=24点、他は0点。通常回答8問、100の支持8問、最大候補は100のみなので、L100・`matched`となる。

### 保存するプロフィール

`state.json`内の`profile`には次を保存する。AIが計算結果を記入する入力形式とは分ける。

| フィールド | 内容 |
| --- | --- |
| `catalog_version` | 質問・対応・指示の版。現行は`"0.2.0"` |
| `answers` | q1〜q8の選択ID配列。主副の順序と特別な回答を保持 |
| `level` | プログラムが決めた内部L |
| `selection` | 次表の計算過程 |

| `selection`のフィールド | 内容 |
| --- | --- |
| `algorithm` | 規則の識別子`"balanced-choice-v1"` |
| `reason` | 第5節の五つの理由のいずれか |
| `answered_count` | 通常回答のある設問数 |
| `scores` | `"80"`〜`"130"`の六つのキーと整数の素点 |
| `support` | 各アンカーを支持した異なる設問IDの配列 |
| `top_candidates` | 正の最大点を持つアンカーの整数配列。得点なしなら空配列 |
| `contributions` | 通常の各選択について、設問・選択・順位・アンカー・加算点を記録した配列 |
| `special_answers` | 特別な回答がある設問IDと、`context`・`none`・`skip`の対応 |

`contributions`の各要素は`question`、`choice`、`rank`、`anchor`、`points`を持つ。`rank: 1`は単独回答または主回答、`rank: 2`は副回答である。単独回答の`points`は3、主回答は2、副回答は1となる。特別な回答はこの配列へ加点として追加しない。

再適用や説明時は、保存された回答と同じ版のカタログからプロフィールを再計算し、保存されたLと計算過程全体が一致するかを確認する。Lだけ、理由だけ、寄与だけを自由に書き替えたプロフィールは、そのまま採用しない。保存済み設定の再利用で、もともとの`reason`を「再利用」に上書きすることはない。

## 7. 回答由来の補助指示

Lは主構成を選び、一部の回答には課題に応じた補助指示も残す。補助指示は主構成の中で必要な内容を補い、別のLへ自動変更する理由にしない。同じLでも、選択した補助指示や今回の課題によって応答は変わる。

0.1.0の28規則から、次の8規則を文面を変えずに保持した。表の選択IDは0.2.0のもの。

| 補助指示ID | 対応する選択 | 反映する内容 |
| --- | --- | --- |
| `concrete_trial` | q1A、q2F、q5C | 試行が有用な課題で、試し方・観察結果・次の判断を示す |
| `familiar_comparison` | q1E | 既知との共通点・違い・比較の限界を示す。既知の内容を決めつけない |
| `decision_changing_information` | q2A | 判明すると判断が変わる情報と、確かめ方を示す |
| `participants_goals` | q3A | 意見の違いを、各人の明示された目的と結びつける |
| `recent_concrete_case` | q4D | 調査に使える直近の一件から、期待・結果・証拠を整理する |
| `success_comparison` | q4B | 成功時と失敗時の差を調べる。比較対象がない場合は示す |
| `revise_applicability` | q6C | 反例があるとき、適用範囲・必要条件・修正すべき範囲を点検する |
| `work_back_from_goal` | q7D | 明示された目標から必要な作業・条件を逆にたどる |

これらが付くのは48選択肢中10個で、残る38個の`preference_ids`は空配列である。空配列でも、その選択肢のアンカーへの支持点は残る。意味を推測して補助指示を増やさない。

新質問で未使用となった次の20規則は`preference_rules`から外した。共通品質または主構成との重複、新しい選択文から直接導けない内容を、回答由来の追加指示として残さないためである。

`purpose_and_context`、`principles_and_rules`、`priorities_and_options`、`impact_and_reversibility`、`supporting_facts`、`explicit_assumptions`、`applicability_conditions`、`trace_sequence`、`relationships_and_conditions`、`nonnegotiable_conditions`、`pros_and_cons`、`hard_to_change_parts`、`alternative_explanations`、`more_observation`、`decompose_problem`、`concrete_example`、`next_action`、`reason_to_conclusion`、`compare_rejected_options`、`other_viewpoints`。

事実確認、理由、必要な条件・例外、行動などの共通品質を外した変更ではない。共通品質指示7本は0.1.0から原文のまま保持している。旧版の保存設定を、この削除を理由に書き換えない。

## 8. 自動選定と数値フェード

この自動選定が返す候補は次の11個である。

```text
80, 85, 90, 95, 100, 105, 110, 115, 120, 125, 130
```

六つのアンカーに加え、隣接する二つが最大で同点の場合にだけ五つの中点を使う。仮設定100もこの集合に含まれる。

指示の生成機構`render_instructions`は、80〜130の全51整数を受け取れる。隣接アンカーaとbの間では、次の比率で二つの指示を組み合わせる。

```text
上側の指示の重み = (L - a) / (b - a)
下側の指示の重み = 1 - 上側の指示の重み
```

たとえばL93なら90の指示を7/10、100の指示を3/10にする。これは指示上の指定であり、生成文の30%が特定の構造になる保証ではない。51整数を扱えることと、初回8問から1点単位で人物の特徴を測定できることは別である。外部入力へ任意の`level`を渡す機能は設けていない。

## 9. 手計算の確認例

次の入力はすべて0.2.0の架空回答である。順番はq1〜q8。`B>D`は主回答B・副回答Dを表す。旧案のA〜Dとは意味が異なる。

| ケース | 入力 | 最大点と支持 | 期待L | 理由 |
| --- | --- | --- | ---: | --- |
| 一件 | `A F E D C B B C` | 80に24点・8問 | 80 | `matched` |
| 目的と作業群 | `C B A F E D D A` | 90に24点・8問 | 90 | `matched` |
| 共通基準の比較 | `E D C B A F A F` | 100に24点・8問 | 100 | `matched` |
| 条件の分岐 | `B A F E D C F D` | 110に24点・8問 | 110 | `matched` |
| 要素間の関係 | `F E D C B A E B` | 120に24点・8問 | 120 | `matched` |
| 捉え方の比較 | `D C B A F E C E` | 130に24点・8問 | 130 | `matched` |
| 80と90の隣接同点 | `A F E D E D D A` | 各12点・各4問 | 85 | `adjacent_blend` |
| 90と100の隣接同点 | `C B A F A F A F` | 各12点・各4問 | 95 | `adjacent_blend` |
| 100と110の隣接同点 | `E D C B D C F D` | 各12点・各4問 | 105 | `adjacent_blend` |
| 110と120の隣接同点 | `B A F E B A E B` | 各12点・各4問 | 115 | `adjacent_blend` |
| 120と130の隣接同点 | `F E D C F E C E` | 各12点・各4問 | 125 | `adjacent_blend` |
| 非隣接の同点 | `A F E D F E C E` | 80と130に各12点・各4問 | 100 | `mixed` |
| 三候補の同点 | `A F A F A F context none` | 80・90・100に各6点・各2問 | 100 | `mixed` |
| 通常回答が2問 | `E D context none skip skip skip skip` | 100に6点・2問 | 100 | `insufficient_answers` |
| 隣接同点だが一方の支持が1問 | `A B>D D>A skip skip skip skip skip` | 80と90に各3点。支持は80が1問、90が2問 | 100 | `insufficient_support` |

最初の六例は8問×3点、続く五つの中点例はそれぞれ前半4問と後半4問に分けた4問×3点なので、24点または12点ずつになる。この配置から手計算で期待値を置ける。

最後の例はq1Aから80に3点、q2Bから90に2点・q2Dから100に1点、q3Dから120に2点・q3Aから90に1点である。80と90は同じ3点でも、80の支持が一問しかないため85にはしない。

これらは規則の計算例であり、実際の利用者の回答分布、正答率、本人への適合率ではない。

## 10. 理由の確認と旧版の扱い

### 明示的な確認

利用者が選定理由や内部値を求めた場合は`explain`で確認する。現在の0.2.0プロフィールについては、次をJSONで表示する。

| 出力 | 意味 |
| --- | --- |
| `configured` | 保存済みプロフィールがあるか |
| `verified` | 回答から再計算したプロフィールと保存内容が一致したか |
| `catalog_version` | 保存プロフィールの版 |
| `level` | 実際の保存値 |
| `reason_message` | 保存された理由に対応する説明 |
| `selection` | 第6節の計算過程 |
| `answers` | 設問ID・質問文と、選んだID・文面。主副の順序を保持 |
| `interpretation` | 再計算による一致と、本人への適合性の未検証を区別する説明 |

`answers`は、各要素が`question`、`text`、`selected`を持つ配列である。`selected`の要素は`choice`と`text`を持つ。通常の応答や`status`ではこの一覧と内部値を出さない。`explain`は読み取り専用で、質問の取り直しや`apply`を実行しない。

`verified: true`は、この規則で保存結果を再現できたという意味である。現行版の保存形式が不正、または再計算と不一致ならエラーとなり、その結果を検証済みとして表示しない。本人に適している、理解が改善した、回答が本人の全場面の特徴を表す、といった意味を加えない。

### 0.1.0からの移行

更新インストールは、有効な0.1.0のプロフィールと旧指示を保持する。プログラムとセットアップSkillを更新しても、旧選択IDを新しい表へ対応させない。明示的な再設定で0.2.0の8問を取り直し、その新しい入力を適用するときに新方式へ移る。

旧0.1.0への`explain`は`verified: false`と`method: "legacy-host-selection"`を返し、保存されている`catalog_version`、`level`、`answers`、`evidence`だけを説明対象にする。旧回答は保存IDのままで、新版の質問文へ展開しない。新しい`selection`や得点を作らず、旧ホストAIの判断理由も推測しない。未設定の場合は`configured: false`とその旨を返す。

Codexの日常用Skill・プロフィール・短いAGENTS呼び出し指示の配置と、Claude Codeの個人用指示への適用は[README](../README.md)に記載している。旧設定の保持と再設定を、利用者のPCでのインストール確認やホストの毎応答での動作確認と混同しない。

## 11. 検証の境界と根拠

この実装で再現できるのは、回答の受け取り、素点と支持の集計、決定規則、保存値との整合、指示ファイルの生成である。人が選択肢を意図どおり読むか、構成の違いを出力から識別できるか、好み・理解・作業結果・速度が改善するかは別の評価対象である。通常の初回設定に長文試験を追加して確認する仕様にはしていない。

関連研究から借りている範囲は、説明の忠実性、情報のつなぎ方、経験による違い、好みと成果を分ける評価、規則の用途に沿った検証、利用者による確認・再設定である。六つの構成、順序、8問×6択、3・2・1、閾値を次の文献から導いたとは説明しない。詳しい確認箇所と適用の限界は[根拠資料の参考文献](evidence-and-design-rationale.md#10-参考文献と確認範囲)を参照する。
