# Lと初回質問の再設計案

作成日: 2026-11-01

状態: **設計案。現行の設定プログラムには未反映。** 現行カタログは0.1.0で、この文書を追加しても保存済みの回答・L・個人用指示は変更されない。

## 目的と前提

初回の固定8問で考え方の選択を受け取り、本人が毎回数値を指定しなくても、AIが説明をその人に合わせられるようにする。日常の文章の長さ、語彙、敬語、誤字、応答速度、経歴から推測しない。

LはAIの説明の組み立て方を選ぶ内部設定である。IQ・知能・能力・性格を測定した値ではない。80〜130という数字と、実在の同じIQ値を持つ人の特徴との対応は主張しない。

この設計で作る対応表は、説明方針を選ぶための**設計上の仮説**である。実際の理解しやすさや本人への適合性は未検証であり、決定規則の再現性と、その規則の有用性を分けて確かめる。

## 1. Lで変えるもの

説明全体を組み立てる際に、何を主な単位として扱うかを切り替える。

| L | 主な単位 | 本文の主構造 | 隣の段階との違い |
| --- | --- | --- | --- |
| 80 | 一件の具体的な対象・操作 | 実際の一件をたどり、条件・理由・判断・次の操作をつなぐ | 一件を追って理解する |
| 90 | 目的に沿った作業のまとまり | 目的を置き、必要な作業群と各作業の役割を結びつける | 個々の操作を目的のあるまとまりにする |
| 100 | 選択肢と共通の判断基準 | 基準をそろえて選択肢を比較し、採用理由を示す | 作業のまとまりから、代案の比較へ進む |
| 110 | 前提と条件による分岐 | どの条件ならどの判断になるかを分け、条件変更時の判断を示す | 一つの比較結果を、成立条件ごとの判断に分ける |
| 120 | 要素とその相互関係 | 構成要素・依存関係・作用を示し、変更が他の要素に及ぼす影響を説明する | 分岐の列挙から、要素が影響し合う全体の構造へ進む |
| 130 | 説明や判断に使っている枠組み | 複数の説明・判断の枠組みを比較し、現時点で採る枠組みと、見直す観測条件を示す | 一つの全体構造から、その構造の捉え方自体を比較・改訂する |

この順序は、個別の操作から、操作のまとまり、比較、条件分岐、要素間の関係、枠組み自体の検討へと、説明の主な単位を移すための設計である。人間の能力の順位、等間隔の心理尺度、実証された難易度の順序ではない。

### 全Lで共通に維持するもの

- 確認済みの事実、重要な条件、例外、不確実性、根拠、次の行動。
- 調査・推論・整理・実装・レビュー・検証の品質。故意の誤答、手抜き、遅延を行わない。
- 明示された要件と、作業対象のプロジェクトのルール。
- 平易な言葉と、必要な専門用語の正確な使用。
- 依頼に見合う長さ。単純な質問に6段階の構造を無理に当てはめない。
- ユーザーが今回指定した説明方法の優先。通常の会話だけで保存済みLを変更しない。

L130だけが根拠や反例を考え、L80では考えない、という仕様にはしない。各段階の違いは、同じ必要情報をどの構造で提示するかに置く。長さ・難しい語彙・情報の欠落・結論の正誤で差を作らない。

### L120とL130を区別する確認基準

- L120: 一つの捉え方のもとで、要素間の関係と影響を本文の中心に置く。
- L130: 複数の捉え方が何を説明し、どの観測で選び直すかを本文の中心に置く。
- 本当に別の捉え方を検討する必要がない依頼では、L130を理由に無関係な仮説を追加しない。

### L80

B のサーバー対策を選びます。今回の R17 が届く場面を追うと、必要な処理が分かります。

1. 最初に R17 が届いたとき、ジョブを一件作ります。その利用者の ID と R17 を、ジョブと一緒に保存します。
2. タイムアウト後に同じ内容の R17 が再送されたら、新しいジョブを作らず、先に作ったジョブを返します。今は到着ごとに作り、DB に制約がないため、ログでは J41 と J42 ができています。
3. 二つの R17 が同時に届く場合もあるので、DB に `(user_id, request_id)` の一意制約を置き、競合した側は既存ジョブを返します。「先に存在を調べる」だけでは、両方が未作成と判断できます。
4. 新しい出力要求には新しい ID を使い、別ジョブを作ります。別の利用者が R17 を使った場合も別ジョブです。このため、ID と利用者を組にします。

ボタン無効化は二度押しを減らす補助にはなりますが、この自動再送は止められません。必要な再送は残します。制約を入れる前に、既存の重複でどれを残し、実行中のものをどう扱うかを決めてください。

確認では、同じ利用者・同じ ID を順次再送、次に同時送信し、ジョブが一件で、同じジョブ ID が返ることを見ます。別 ID と別利用者では別ジョブになることも確認します。

さらに、作った一件がキューから再配信される場合を試します。ワーカーが出力を重複させないかは未確認です。作成を一件にしても、この点は保証されません。一要求・一ジョブなのに出力が重複するなら、次は作成処理ではなく実行処理を調べます。

### L90

B のサーバー対策を選びます。目的を満たす仕事を、「同じ要求をまとめる」「別の要求を分ける」「作成後の結果を確かめる」に整理します。

【同じ要求を一件にまとめる】
自動再送は残す必要があります。今回も同じ利用者の R17 がタイムアウト後に二回到着し、J41 と J42 ができています。今の API は到着ごとに作り、DB に制約がありません。そこで `(user_id, request_id)` に一意制約を置き、競合時は既存ジョブを返します。先に存在を調べるだけでは同時到着を処理しきれません。ボタン無効化は二度押しの補助であり、この再送への対策にはなりません。

【別の要求を別ジョブに分ける】
新しい出力要求には新しい ID を使います。同じ ID でも利用者が違えば別ジョブです。そのため、要求 ID だけでなく利用者も一意制約に含めます。同一利用者・同一 ID の順次再送と同時送信では一件かつ同じジョブ ID、別 ID と別利用者では別ジョブ、という確認を組にして行います。

【作成後の結果を確かめる】
キューには再配信があるため、作成が一件でも同じジョブが再実行される場合があります。ワーカーが出力を重複させないかは未確認なので、再配信を試して確認します。一要求・一ジョブなのに出力が重複するなら、調査する仕事を作成処理から実行処理へ移します。

導入の準備として、既存の重複でどれを残すかと、実行中のジョブの扱いを先に決めてください。そのうえで一意制約と競合時の処理を入れ、上の確認を行います。作成の一意性と、再実行時の出力の一意性は、それぞれ確認が必要です。

## 3. 質問とLの対応

現在の固定8問と選択肢の文面をそのまま使う試案である。質問の選択肢は、人物の能力として解釈せず、説明の主構造を選ぶ手がかりとして対応づける。

補助指示は、選ばれた主構造の中へ必要な内容を置く役割とする。たとえばL80で「前提を確認する」が選ばれていれば、具体的な一件を追う中で前提を確認する。その回答だけを理由に説明全体をL110の条件分岐へ戻さない。必要な品質条件を省く許可にも使わない。

数値の集合は、その回答を足場にする応答構成として互換性があると**設計者が指定した**アンカー。集合にあるアンカーの fit=1、それ以外=0。空集合は、補助指示には反映するがLを区別する直接の支持点には使わないという意味。主回答・副回答の重み配分には含める。

| 問 | A | B | C | D |
|---|---|---|---|---|
| q1 初めての道具・仕組み | 実際に試す → {80} | 目的と全体での位置 → {90} | 原理・規則 → {120} | 既知との共通点・違い → {90,100} |
| q2 情報不足での判断 | 小さく試す → {80} | 判断が変わる情報 → {110} | 優先順位と候補比較 → {100} | 失敗の影響とやり直せる範囲 → {110} |
| q3 意見の食い違い | 支える事実 → {} | 各人が達成したいこと → {90} | 各意見の前提 → {110,130} | 各意見が成り立つ条件 → {110,130} |
| q4 作業の不調 | 直近の具体的な一件 → {80} | 成功時との比較 → {100} | 手順を順にたどる → {80,90} | 他の作業・周辺条件との関係 → {120} |
| q5 得失のある選択 | 必ず満たす条件 → {100,110} | 利点・欠点の比較 → {100} | 小さく試す → {80} | 後から変更しにくい部分 → {110} |
| q6 合わない事例 | 事実関係の確認 → {} | 当てはまる範囲の見直し → {110,130} | 別の説明 → {130} | 追加の観察・試行 → {80} |
| q7 複雑な問題 | 小さな問題に分ける → {90} | 全体の関係 → {120} | 目標から逆に必要なことをたどる → {90} | 具体例一つ → {80} |
| q8 結論の確定前 | 次の行動 → {80} | 理由と結論のつながり → {} | 他の選択肢を退けた理由 → {100} | 別の視点からの確認 → {130} |

### この対応を置く理由と限界

- q1A/q2A/q5Cの同じ concrete_trial は、同じ {80} にそろえる。q4D/q7B の relationships_and_conditions は {120}、q3A/q6A の supporting_facts は空集合にそろえる。文字A〜Dに共通点数はない。
- q3A/q6Aの事実確認とq8Bの理由・結論の接続は、全Lで保持する共通品質なので、特定Lの支持として使わない。既存 preference_rules は従来どおり生成する。回答を無視することとは異なる。
- q1Dは比較対象をまとまりとして整理する90と、共通の観点で比較する100の双方に対応させる。q4Cは一操作ずつの追跡80と、作業のまとまり90の双方に対応させる。
- q5Aは比較基準100と、条件を満たす／満たさない分岐110の双方に対応させる。
- q3C/Dは複数の意見がある場面で、条件分岐110と、意見を支える枠組みの比較130の双方に対応させる。q6Bは適用範囲の分岐110と、枠組みの適用範囲を改訂する130の双方に対応させる。
- q1Cの原理・規則は、対象の要素とその関係を組み立てる120へ対応させる。この短い回答だけで「システム思考型」を実証できるわけではない。q8Dを130に対応させることも、枠組みを比べる構成を採るという設計上の約束であり、人物の特性の推論ではない。
- q6Dは単に観察・試行を追加する選択なので130には対応させない。何を実施し何を観察するかを足場にする80へ対応させる。
- これらは解釈を含む著者の対応表である。透明にしただけで科学的に正しくなるわけではない。特にq1C/q1D/q3C/D/q4C/q8Dの対応は、実際の出力例で利用者が納得するか確認する必要がある。

## 4. 選定方法の具体案

### 比較した方式

| 方式 | 判断 |
| --- | --- |
| ホストAIに回答と指示文の照合を任せる現行方式 | 選ぶ境界が明示されず、同じ回答でも選定の再現性を確認しにくい。選定理由も質問IDだけでは十分に記録できない。 |
| 各選択を一つのLに換算して平均する | 離れた構成への支持が混在した場合に、どちらも支持していない中間の構成を選んだように説明してしまう。採らない。 |
| 固定対応表の支持点を単純に加算する試案 | 再現できるが、L80を支持できる設問は7問、L120は3問あり、得点上限が異なる。比較用スコアを補正する。 |
| 固定対応表と、得点上限をそろえる補正を使う試案 | 今回の候補。回答・対応表・計算・選定理由を分けて追跡できる。対応表の適合性まで実証するものではない。 |

### 計算

1. q1〜q8が揃っていること、各問の通常回答は一つまたは異なる二つであることを検証する。`context`・`none`・`skip`はそれぞれ単独で受け付ける。未回答を勝手に`skip`へ変換しない。
2. 一つ選んだ設問の重みは3、二つ選んだ場合は主回答2・副回答1とする。二つ選んだ設問の総重量を増やさない。
3. 対応表にある各Lへ、その回答の重みを加算する。一つの回答が二つのLに対応するときは、両方に同じ重みを加算する。
4. 各Lの加算値を、固定8問で得られるそのLの最大値で割り、比較用スコアにする。分母は回答内容・スキップ数で変更しない。
5. 浮動小数点の丸めで同点を崩さないよう、整数比として比較する。Pythonでは`fractions.Fraction`で表せる。

| L | 支持する選択肢がある設問数 | 得点の最大値 | 比較用スコア |
| --- | ---: | ---: | --- |
| 80 | 7 | 21 | 加算値 / 21 |
| 90 | 4 | 12 | 加算値 / 12 |
| 100 | 5 | 15 | 加算値 / 15 |
| 110 | 4 | 12 | 加算値 / 12 |
| 120 | 3 | 9 | 加算値 / 9 |
| 130 | 3 | 9 | 加算値 / 9 |

この補正は**支持できる設問数による得点上限の差**をそろえる。各Lに対応する選択肢の数や、実際の利用者がその選択肢を選ぶ頻度まで同じにはしない。たとえばL120とL130はどちらも3問で支持できるが、対応する通常選択肢の数は異なる。

比較用スコアは確率、適合率、確信度、IQではない。満点でも、その人に最適な説明だと証明されたことにはならない。重み3・2・1や後述の閾値も、測定から得た係数ではなく、試案として置く運用規則である。

直接の支持点がない選択肢も、主回答・副回答の配分には含める。たとえばq6をDだけにすればL80に3点、Dを主回答・Aを副回答にすればL80に2点で、Aからの直接の支持点は0になる。全L共通の品質を重視したことを、低い能力などへ読み替えない。

### 判定の順序

1. A〜Dを選んだ設問が3問未満なら、運用上の仮設定L100とし、理由を`insufficient_answers`にする。通常回答でも直接の支持点がない選択は回答数に含む。
2. 6候補すべての**比較用スコアの最大値**と、最大値の候補集合を求める。
3. 最大値が0、または最大候補のどれか一つでも、支持する設問が2問未満なら、仮設定L100・`insufficient_support`とする。支持設問数はIDで数え、同じ設問の主回答と副回答を2問と数えない。低いスコアの候補を繰り上げない。
4. 最大候補が一つなら、そのLを選び`matched`とする。L100にもこの通常選択がある。
5. 最大候補がちょうど二つで差が10なら、中点を使い`adjacent_blend`とする。例: 80と90なら85。
6. 最大候補が非隣接の二つ、または三つ以上なら、仮設定L100・`mixed`とする。離れた候補を平均して別の構成を支持したことにしない。

通常の初回利用では数値を見せず、未決定理由に応じて「複数の進め方が同程度に選ばれたので、基本設定で始める」などと伝える。ユーザーが設定や理由を尋ねた場合は、保存した内容を確認できるようにする。

### 数値のフェードについて

この選定試案が自動で選ぶのは、80・85・90・95・100・105・110・115・120・125・130の11候補である。中間の5刻みは、隣り合う2候補が最大で同点になった場合だけ使う。

既存の80〜130の整数を受け取り、隣接する指示文を補間する機構は維持する提案である。自動選定の候補数と、内部の指示生成が受け付ける値の範囲を混同しない。1点ごとの違いを回答から精密に測れるとは主張しない。異なる主構造を混ぜたときに自然な回答になるかは、実際の出力で別途確認する。

## 5. L100の理由と、再利用を区別する記録

| 選定理由 | 実際に記録する意味 | L100の場合の説明 |
| --- | --- | --- |
| `matched` | 一つの構成が最大で、複数の設問から支持された | 比較基準を軸にする構成が、この規則で選ばれた |
| `adjacent_blend` | 隣接する二構成が最大で同点 | この試案の中点は85等であり、100にはならない |
| `insufficient_answers` | 通常回答が3問未満 | 材料不足による仮設定 |
| `insufficient_support` | 最大候補の支持が複数の設問にまたがらない、または支持点がない | 判断根拠不足による仮設定 |
| `mixed` | 離れた候補、または三つ以上の候補が同点 | 進め方を一つに絞れないための仮設定 |

保存済み設定の再利用は、選定理由と別の操作情報にする。再利用のたびに元の`matched`や`mixed`を上書きしない。

以下は新しい保存形式の**説明用の候補例**であり、利用者本人の結果ではない。

```json
{
  "profile": {
    "level": 100,
    "selection": {
      "rule_version": "0.2-design-2",
      "reason_code": "matched",
      "top_candidates": [100],
      "support_questions": ["q1", "q2", "q4", "q5", "q8"]
    }
  },
  "operation": {
    "action": "created_from_answers"
  }
}
```

再利用した場合の操作情報は`reused_saved_profile`とする。これはプロフィールを新たに判定したという意味ではない。実装時は回答と対応表の版から、L・選定理由・寄与をローカルで計算し、ホストAIに任意のLや理由を自由生成させない。選定結果の整合性も再計算して検証する。

通常の会話から回答やLを更新しない。新しい対応表で旧版の保存済み回答を暗黙に再解釈せず、明示的な再設定で取り直す。今回の作業ではその移行は行っていない。

入力はq1〜q8の順。`D>A`は主回答D・副回答A、`skip`は本人が明示的に回答を見送った場合を表す。以下は架空の回答であり、利用者本人の回答ではない。

85の例でq6の`D>A`を`D`へ変えると、80への加算値は14から15へ増え、80の15/21が90の8/12を上回る。結果は80/`matched`となる。これはAに低いLの意味があるためではなく、主回答Dへの重みが2から3へ変わるためである。

## 7. 全組合せの算術確認で分かったこと

A〜Dを各問一つずつ選ぶ全65,536通りを列挙して比較した。**これは実際のユーザーの回答分布、適合率、現行アプリの選定結果の統計ではない。** 同じ固定表に対する、二つの未実装案の計算上の比較である。

| 試案 | 規則により100を選んだ組合せ | 判断できず仮の100を使う組合せ | 100になる合計 |

| 単純加算 | 7,008 | 20,201 | 27,209 |

100以外が増えたことを、選定の正しさや本人との相性改善の証拠にしない。今回確認できたのは、上限補正による計算結果の変化、手計算例との一致、候補の到達性までである。得点機会以外の偏りは残り、特に別の視点とL130の対応などは、実際の回答例を用いて見直す余地がある。

## 付録: 選定規則を再現する純粋関数

入力形状の検証済みの回答を受け取る、設計確認用のコード。ファイル保存、個人設定の変更、モデル/API呼出は行わない。実装時には既存の回答形式検証を先に適用する。

```python
from fractions import Fraction

LEVELS = (80, 90, 100, 110, 120, 130)
FIT = {
    'q1': {'A': (80,), 'B': (90,), 'C': (120,), 'D': (90, 100)},
    'q2': {'A': (80,), 'B': (110,), 'C': (100,), 'D': (110,)},
    'q3': {'A': (), 'B': (90,), 'C': (110, 130), 'D': (110, 130)},
    'q4': {'A': (80,), 'B': (100,), 'C': (80, 90), 'D': (120,)},
    'q5': {'A': (100, 110), 'B': (100,), 'C': (80,), 'D': (110,)},
    'q6': {'A': (), 'B': (110, 130), 'C': (130,), 'D': (80,)},
    'q7': {'A': (90,), 'B': (120,), 'C': (90,), 'D': (80,)},
    'q8': {'A': (80,), 'B': (), 'C': (100,), 'D': (130,)},
}
SPECIAL = {'context', 'none', 'skip'}

def select(validated_answers):
    scores = {a: 0 for a in LEVELS}
    supports = {a: set() for a in LEVELS}
    answered = 0
    for qid in FIT:
        choices = validated_answers[qid]
        if choices[0] in SPECIAL:
            continue
        answered += 1
        weights = (3,) if len(choices) == 1 else (2, 1)
        for choice, weight in zip(choices, weights):
            for anchor in FIT[qid][choice]:
                scores[anchor] += weight
                supports[anchor].add(qid)
    maximum_scores = {a: 3 * sum(any(a in targets for targets in choices.values())
                                for choices in FIT.values()) for a in LEVELS}
    comparison = {a: Fraction(scores[a], maximum_scores[a]) for a in LEVELS}
    maximum = max(comparison.values())
    top = [a for a in LEVELS if comparison[a] == maximum]
    if answered < 3:
        level, reason = 100, 'insufficient_answers'
    elif maximum == 0 or any(len(supports[a]) < 2 for a in top):
        level, reason = 100, 'insufficient_support'
    elif len(top) == 1:
        level, reason = top[0], 'matched'
    elif len(top) == 2 and top[1] - top[0] == 10:
        level, reason = sum(top) // 2, 'adjacent_blend'
    else:
        level, reason = 100, 'mixed'
    return {
        'level': level, 'reason_code': reason,
        'substantive_count': answered,
        'scores': scores, 'top_candidates': top,
        'maximum_scores': maximum_scores,
        'comparison_scores': {a: str(comparison[a]) for a in LEVELS},
        'support_questions': {a: sorted(supports[a]) for a in LEVELS},
    }
```
